# Структура контента

## Главный принцип

`local-content/current/` — единственный локальный источник истины для контента
приложения. Для каждого используемого фото или видео внутри проекта хранится
только актуальная подготовленная версия. Отдельный архив тяжёлых оригиналов не
ведётся.

Несколько файлов у одного дня допустимы, только если это разные части контента:
например, десять фотографий карусели или видео вместе с его обложкой.

## Папки

```text
local-content/                  # целиком локальная, Git её игнорирует
  current/                      # актуальная версия приложения
    content.mjs                 # описания всех настроенных дней и список медиа
    media/                      # единственные актуальные фото и видео
      days/<day>/               # материалы конкретного дня
      days/video/               # общие материалы видео-шаблона
  credentials/                  # ключ и пароли; никогда не публикуются
    cek.json
    passwords.json
    backups/                    # резервные записи ключей, не медиаконтент
```

Папки с учётными данными доступны только владельцу компьютера (`700`), а сами
файлы — только на чтение и запись владельцем (`600`). `npm run audit:vault`
проверяет это вместе с целостностью сейфа.

## Как загружать фото и видео

Пользователь может:

- приложить файл прямо к сообщению;
- положить его в `local-content/current/media/days/<day>/`;
- положить его в любое другое место проекта и сообщить, для какого дня он нужен.

Обязательно указать день и, если это не очевидно, сказать: файл заменяет
существующий или добавляется как отдельная часть контента.

Агент самостоятельно:

1. Находит полученный файл и определяет итоговый путь.
2. Создаёт оптимизированную версию во временном месте: исправляет ориентацию,
   уменьшает разумный размер, удаляет метаданные и приводит к совместимому с
   браузером формату.
3. Проверяет, что итоговый файл открывается, имеет ожидаемые размеры или
   длительность и не потерял заметно качество.
4. Только после проверки помещает его в
   `local-content/current/media/days/<day>/` и атомарно заменяет прежнюю версию,
   если это замена.
5. Удаляет из проекта исходный тяжёлый файл, старую версию и точные дубликаты,
   если они больше не используются.
6. Обновляет `local-content/current/content.mjs` и список `secretMedia`.
7. Проверяет соответствие текущего контента и зашифрованного vault.

Агент не должен удалять единственную рабочую копию до успешной проверки новой.
Внешний временный attachment не обязан сохраняться после подготовки актуальной
версии.

## Остальной контент

### Категория дня

Каждый день в `content.mjs` обязан иметь одну явную `category`: `compliment`,
`photos`, `cert`, `coupon`, `restaurant` или `video`. Это единый источник для
иконки календаря, вкладки архива и цветового акцента. Категория описывает смысл
дня, а не внутренний вид карточки: гибридный комплимент может, например,
содержать сертификат. `npm run audit:vault` проверяет допустимость категории и
наличие соответствующего основного контента.

### Текст, подпись, купон или сертификат

Достаточно прислать текст и назвать день. Агент обновляет
`local-content/current/content.mjs`. Пароли, сертификатные коды и личные тексты
нельзя переносить в README, обычные документы или публичные папки.

### Figma и референсы

Исходник можно приложить к сообщению. Если он становится частью приложения,
агент оставляет только подготовленную актуальную версию:

- личное медиа — в `local-content/current/media/`;
- намеренно публичную графику — в подходящей папке `public/`;
- кодовую иллюстрацию или системную иконку — в `src/` по правилам UI kit.

Отдельная постоянная папка с дублирующими Figma-выгрузками не создаётся.

## Что нельзя хранить в public

`public/` содержит только намеренно публичные общие ассеты и зашифрованный
`public/vault/`. Личных незашифрованных фото, видео, паролей, кодов и пустых
папок категорий там быть не должно.

`dist/` — временный результат сборки. Его можно удалить; `npm run build`
создаст его заново.

## Публикация контента

1. Подготовить единственную актуальную версию в `local-content/current/`.
2. Запустить `npm run encrypt`.
3. Убедиться, что vault `keyId` не изменился и `npm run verify:release` прошёл.
4. Публиковать только изменённый зашифрованный `public/vault/` после явного
   подтверждения пользователя для новых личных медиа.
